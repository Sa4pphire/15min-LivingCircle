# 普通与合成分析的有界调度

`POST /api/v1/analyses` 与 `POST /api/v1/synthetic-analyses` 共享一个调度器。
通过请求结构校验后，最多有 2 个分析任务执行、8 个任务准备输入或排队。
超过待处理容量的请求在读取路网前返回 503，不创建任务记录或启动引擎。

这一步接通了真实 API 的准入与消费流程。在线采样、局部实验仍采用原有
`BackgroundTasks`；它们以及 POI 路线、编辑器的直接计算尚未纳入这一预算。
因此当前的限制是这两个分析入口的任务数量，不是全服务 C++ 进程总数。

## 请求与名额的生命周期

```text
API reserve
  ├─ 无名额 → 503 + Retry-After: 1
  └─ 有名额 → 在线程池准备输入
                 ├─ 准备失败 → release → 原输入错误响应
                 └─ 创建共享状态 → submit
                                      ├─ 失败 → 删除记录 + release → 503
                                      └─ 成功 → 202
                                                  ↓
消费者取出任务 → 归还待处理预约 → 执行业务函数 → 保留终态供 GET 查询
```

预约表中的 `reserved` 与 `queued` 合计不超过 8。预约、提交、释放与出队
转换都在同一事件循环线程执行，中间没有 `await`。同步文件读取与输入转换
使用线程池，线程只返回准备结果，不操作调度器或任务状态字典。

调用方在提交成功前持有预约。准备失败、取消或提交失败都由调用方归还；
入队成功后转交调度器，直到出队或关闭丢弃时才释放。任务结果记录的保留
与预约无关，任务完成不会自动删除 GET 所需的结果。

取消等待线程不会停止实际文件读取。因此请求取消后仍等待该准备结束，
再由 `finally` 归还预约；服务关闭后也允许归还尚未提交的预约。

## HTTP 契约

请求、202 响应及 GET 状态字段保持兼容。202 只表示已经接受调度；
返回的 `queued` 是接单响应的快照，客户端应继续用任务 ID 查询状态。

容量已满或调度器关闭时：

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json
```

响应体见 [过载响应示例](../contracts/analysis-busy.response.example.json)：

```json
{"detail":{"code":"ANALYSIS_BUSY","message":"分析任务已满或服务正在关闭，请稍后重试"}}
```

不支持的区域等既有输入错误保留 422。前端现有的 `detail.code/message`
解析可以显示过载错误；没有为 POST 增加自动重试或幂等保证。

## 状态、日志与耗时

`ScheduledAnalysis.state` 直接引用 `_analyses[id]` 中的同一个对象。
业务函数自行记录的 `failed` 不会因为函数正常返回而被覆盖为成功。
首次结果、增量结果及 POI 局部失败的既有语义继续由业务流程管理。

调度器统一记录 `analysis.started` 与 `analysis.finished`，API 在成功提交后
记录 `analysis.accepted`。容量拒绝记录 `analysis.rejected`。

| 字段 | 范围 |
|---|---|
| `networkLoad` | 准备输入，包括线程池调度和区域／路网读取转换 |
| `queueWait` | 成功入队至消费者取出；关闭丢弃时记录截至丢弃的等待 |
| `cpp` | 业务流程的第一次完整引擎调用，含编码、启动、通信和解析 |
| `total` | 后台业务执行耗时，不含输入准备、排队和客户端轮询 |

消费者意外异常或取消时会记录失败及执行耗时。尚未开始就被关闭丢弃的
任务没有后台执行 `total`。上述计时不能代替客户端的端到端完成耗时。

RPC 模式不会由 Python 启动 C++ 进程；一个事件循环复用一个通道和 Stub。
客户端计算许可覆盖编码、RPC、本地解析及取消清理，Health 独立。客户端许可
归还不能证明远端 CPU 已停止；当前 C++ 服务的可配置容量门和 RAII 才控制实际应用计算，
在真实结束前仍可拒绝下一请求。RPC 的25秒 deadline不包含前置 JSON 编码，
不自动重试或切回子进程。配置、错误元数据及使用说明见
[引擎说明第14节](../cpp-engine/README.md#14-第四阶段python-可选接入-c-rpc)。

第五阶段将服务端容量配置为 `--compute-capacity N`、Python 客户端容量配置为
`CPP_ENGINE_RPC_CAPACITY=N`，两侧默认2、启动时固定，范围1–2147483647；部署时
人工保持一致。服务端是所有客户端共用的计算上限，客户端配置只限制各自事件
循环里的本地调用。客户端设得更大或旧调用尚未在服务端清理时，仍可能收到繁忙；
设得更小则不能充分使用服务端容量，不自动协商或重试。两个值都设为1可恢复单槽。

满额在业务 JSON 解析前拒绝，没有新增 C++ 应用等待队列。处理函数仍在 gRPC
同步框架提供的线程中执行，门不创建专用线程；poller 配置不是业务计算上限。
每个处理函数独立拥有输入、临时图、距离／前驱、结果和执行控制，继续传整图。
Health 不争计算门，但不代表 CPU／内存隔离。两个分析消费者、8个准备／排队
位置及30秒排队时限保留，不因设置更大 RPC 容量就增加分析消费者数量。
本阶段仅源码审阅，后续明确要求后才验证多请求、超额拒绝、取消回收、Health
及关闭；默认2不代表已测稳定容量，也不构成总线程、连接或内存上限。

## 关闭与当前范围

FastAPI lifespan 启动两个消费者。关闭时停止受理，取消并等待消费者，
随后将未执行的排队任务标记失败并归还其预约。

引擎适配器在取消／超时时终止子进程，并等待同一次通信与进程退出，
之后才传播取消；消费者完成这段清理后才归还执行位置。启动过程中发生
取消也会等到取得进程句柄后终止并回收，健康检查使用相同的清理机制。

本阶段采用立即取消并等待清理的关闭策略。后续仍需完成：全部四类分析
统一调度、30 秒排队过期、终态记录 TTL／容量、统一业务 C++ 许可、探针
预算以及 5 秒优雅退出等待。子进程必须配合 OS 终止，准备工作必须能
结束；本阶段没有另行限制所有清理动作的总时限。

该调度器只在单 Python 服务进程内共享；启用多个服务 worker 会各自创建
预算与内存状态，不会自动形成跨进程的统一上限。

## 本地验证

按项目约定，测试文件留在忽略的 `backend/tests/` 中，不修改忽略规则。

- `test_analysis_scheduler.py`：容量、令牌、失败隔离、异步清理与关闭。
- `test_scheduler_api.py`：两个入口共享预算、拒绝无副作用、准备／提交失败
  回滚、准备线程取消与关闭，以及 POI 阶段取消后结果与日志一致。
- `test_engine_cancellation.py`：用真实 Python 睡眠子进程验证引擎及探针
  的取消、超时、启动竞态和重复取消回收，并验证 v2 成功响应。
- 既有 API、合成分析与分阶段结果测试使用 lifespan 和有界终态轮询。

另外使用兼容的 `walkway/Release/isochrone_engine.exe` 完成一次本地服务
真实 HTTP → 轮询 → C++ → completed 联调。单次联调用于验证链路，
不作为 QPS 或尾延迟结论。
