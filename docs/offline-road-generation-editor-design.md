# 编辑器 OSM 自动道路生成：首版设计建议

日期：2026-10-24。状态：设计草案，尚未实现。

目标：在现有路网编辑器中，框选范围后自动从 OSM 下载原始数据，生成可编辑的步行路网初稿，减少道路描绘和拓扑恢复工作，保留 C++ 多源 Dijkstra。建图阶段允许联网调用 OSM 数据接口，不调用商业路线计算 API；源数据和生成结果缓存后，本地图计算不需要每次联网。首版使用本地参考图，不要求百度地图 AK。

用户最新澄清（2026-10-24）：不要求建图过程完全离线，允许从 OSM 下载数据后自动生成路网。因此默认入口调整为在线下载，用户无需预先准备文件；本地文件导入保留为后续备用入口。本文件名沿用前轮设计路径，正文以本次修订为准。

本轮只阅读源码并编写本设计，未修改业务代码，未安装依赖、导入数据、编译、启动服务或运行测试。以下生成能力和接口均为拟新增，不能视为已可使用。

## 1. 首版用户流程

```text
区域库／编辑器：从 OSM 自动生成路网
  → 在地图框选或输入目标街区范围
  → 确认外围保留范围
  → 自动下载原始道路、节点和相关标签
  → 生成路网初稿和本地参考轮廓
  → 查看道路、来源、排除项与待核问题
  → 创建独立区域
  → 在现有编辑器调整、保存和打包
```

在区域库新增入口；当前编辑器可增加同名入口，但生成过程使用独立预览，创建后由用户决定何时打开新区域。当前画布有未保存修改时不自动切换，也不把 localStorage 草稿当作一定成功的备份。

界面只提供完成任务所需的选择：区域名称、范围、下载生成与创建。原点、规则版本、来源摘要放在详情中，不要求用户手填模型参数或查询语句。范围获取要有 WGS-84 坐标输入或本地参考图等独立入口；在已有百度地图上框选时，必须使用明确的坐标转换，不能把 BD-09 数值直接作为 OSM 查询坐标。

首版先支持有规模上限的小街区在线获取，跑通完整数据链。下载使用 OSM 数据查询服务（如 Overpass），保留节点、道路引用、标签与必要关系；不让用户手动下载或转换文件。后续可增加 `.osm` XML、`.osm.pbf` 备用导入，两类入口进入相同的规范化源模型，不改变建图规则。大范围数据需要单独控制下载、处理和画布显示规模。

## 2. 为什么首先创建新区域

现有“导入 JSON”接受的是同一原点的项目 v2 图，只替换节点、边，不能承担原始 OSM 数据建图。现有新建区域使用 BD-09 原点，而 OSM 坐标是 WGS-84。

首版生成独立 WGS-84 原点的区域，使用现有东西／南北局部米制约定和本地画布。计算轴向为东／北，展示轴向为东／南；记录具体投影方法与支持范围。首版限制街区尺度，较大范围的投影精度另行处理。

新包可以没有百度校准资产，编辑器应明确使用本地参考图。百度底图、百度地点和坐标对齐不是 OSM 自动建图的前提；不能伪造校准文件，也不能只修改坐标类型名称把 WGS-84 图套进 BD-09 区域。

首版不自动把生成图合并进已有区域。合并涉及坐标、重复道路、入口引用、源 ID 和人工编辑基线的迁移，是后续独立任务。

## 3. 生成规则与精度边界

### 保留原始拓扑

先读取 node、way、relation、节点引用和通行标签，再生成计算图；显示几何随后单独简化。共享节点、入口、过街节点及路口端口必须保留。节点或道路 ID 来自稳定的源标识和确定性拆分规则，不靠坐标舍入猜连接。

缺失引用需要显式报告。不能丢掉缺失节点后把其前后节点直接连起来。几何相交或相近不自动建立通行连接；不同层级、桥隧和访问限制必须参与规则判断。

### 分层生成

- 已独立记录的步道和过街优先使用，避免再生成一套重复人行道。
- 普通街段用规则生成步行通道，保留其生成依据；不能把全部道路都无条件设为共享步行空间。
- 普通分侧道路复用既有转换思想，路侧和横穿约束需要保留；不能因为共享机动车中心节点就产生免费过街。
- 双幅道路、复杂路口、桥头、闸门及条件通行等无法可靠处理的对象，进入可定位的待核列表；首版不承诺完整自动处理所有复杂路口。
- 明确禁止步行的道路排除。权限、方向、时段或关系语义超出首版支持范围时，列出原因并采取保守处理，不能静默忽略限制。
- 推断连接与已有记录分开。既没有通行依据、又可能穿过水体或隔离设施的连接不能仅靠距离补上。

来源标记区分“OSM 已记录”“规则推定”“待核查”。OSM 已记录也不等于本项目已经实地核实。输出继续保留 synthetic／unverified 语义，不自动升级为经核实的真实路网。

### 选区与外围数据

编辑范围与计算数据范围分开。预览显示外围保留范围和实际查询范围；在线模式按明确的外围范围请求数据。查询超时、限流或返回不完整响应时不能当作“当地没有路”，应保留已有数据、提供重试或缩小范围的入口。本地文件备用模式中，文件缺少外围数据时应提示提供更大范围的数据。

跨边界街段裁切保留来源和边界标记。过街、转弯等连接不产生半条连接或重复等待，可参考现有区域裁剪规则。边缘结果仍可能受截断影响，不把范围完整当成现实路网完整。

## 4. 预览需要交付什么

预览独立于当前图，不写入当前 graph、不触发当前区域保存：

- 可定位和缩放的候选路网，以及同一坐标系的本地参考轮廓。
- 读取、接受和排除的道路数量；候选图的节点、边及连通分量数量。
- 分侧、共享和过街的生成来源说明。
- 待核列表：缺失引用、受限通行、桥隧层级冲突、复杂路口、重复步道、边界截断等。
- 每项问题能定位到源道路／节点，显示原因；需要时能在创建后继续编辑处理。

连通分量只作线索，不以“分量越少越好”为目标。结构检查通过与 C++ 接受输入只表明格式和模型可计算，不代表现实可通行。

第一阶段重点是生成诊断，不加入双图敏感度排序、人口收益或完整规划分析。

## 5. 保存与重复生成

保存数据建议沿用区域包结构：

```text
source/osm-source.json        规范化源数据：节点、引用、标签、关系与来源
source/generation.json        输入摘要、生成器版本、范围、坐标和生成配置
source/engine-base.json       自动生成的基础 v2 图
source/annotations.json       相对基础图的人工编辑
network.json                  当前可计算图
context.json                  本地参考轮廓
manifest.json                 文件清单、来源和校验和
```

当前区域包只接受 JSON 资产，适合保存下载响应的规范化源 JSON，以及查询范围、获取时间和内容摘要。后续文件导入的原始 XML／PBF 可留在导入缓存，包内仍保存足以重建的规范化源数据。不能只留下 SVG 和最终网络，否则后续仍难以追溯拓扑。

首版可采用现有 engine-snapshot 基线与人工补丁机制，额外保存规范化源和生成配方；必须明确“重新生成”走新建图流程并另存新区域，而不是声称现有 build_base_network 已会读取 OSM 源重建。读取已缓存源数据重建与主动刷新 OSM 数据应区分，避免一次重新生成意外换成新地图版本。

预览确认时直接使用已冻结的候选产物，不能在创建按钮之后悄悄重新生成另一份图。新区域创建后，人工编辑继续使用现有保存、备份、版本冲突和回放逻辑。

规则变化或输入更新后，首版重新生成到新区域。已有 manualGraphEdits 严格绑定旧基础图，不能通过改写摘要强行套用。自动迁移人工改动留到后续阶段。

## 6. 后端接口建议

以下为拟新增接口，尚未实现：

| 接口 | 目的 |
| --- | --- |
| `POST /api/v1/network-editor/road-generation/preview` | 提交 WGS-84 范围和配置，下载／读取缓存，生成独立候选并返回 previewId、摘要、统计和问题 |
| `POST /api/v1/network-editor/road-generation/apply` | 根据冻结预览创建新区域，返回 regionId 与区域版本 |

服务器从预览记录读取候选图，不信任客户端回传的一份替代图。记录绑定源数据摘要、查询范围、获取时间、生成配置、坐标原点、生成器版本和有效期。独立新建没有父区域依赖，不需要虚构一个尚不存在区域的 revision；若接受父区域坐标或快照作为输入，再绑定相应版本与未保存画布摘要。

现有本地编辑接口访问限制继续沿用。下载、解析与生成需要限制响应体积、对象数量、最终图规模、并发和预览保留量，不能只依赖客户端限制。首版按单个小街区生成设计，后台处理避免阻塞普通 API。OSM 下载需有缓存、有限重试和明确失败提示，公共服务不可用时不无限等待。

读取、生成或创建失败时保留已有区域。新包先在临时目录完成文件和清单准备，再发布到新目录；保存前沿用结构与 C++ 输入检查。引擎繁忙时保留预览并允许重试，不另开无预算的引擎通道。

现有 generate_context() 面向显示轮廓，不能原样用作路由生成入口。其下载重试、缓存和选框限制可复用，但当前查询是 out tags geom，后续又简化为 id/kind/d；新分支应查询完整 node、way 引用、标签与必要关系，再分别生成路由图和显示轮廓。主干中心线共享节点不自动意味着可横穿。现有 BD-09 分支的百度转换需求也不能被“OSM 可下载”掩盖。

## 7. 分阶段交付

1. **首版：框选范围 → 自动下载 OSM → 生成初稿／疑点 → 独立预览 → 新建 WGS-84 区域 → 编辑保存。** 同步保存完整来源，列出未支持和待核对象。只把这条流程作为首个主要学习主题。
2. **第二阶段：更完整的生成规则与备用数据入口。** 增加双幅路和路口细化，按需支持 XML／PBF 文件导入；保持同一源模型，避免重新造解析后的业务管线。
3. **第三阶段：核查价值排序。** 在生成疑点之上增加保守／宽松情景，优先处理会改变 15 分钟覆盖结论的位置。
4. **后续：已有区域的更新与人工编辑迁移。** 先显示冲突和差异，再讨论可安全合并的范围。

首版预期好处是减少机械描线和“先丢失、再恢复”原始拓扑的工作，不预先承诺精度、节省比例或自动完成所有路口。评估时应分别记录输入完整性、拓扑错误、人工修正量和覆盖误差。本轮没有执行这些验证；后续仅在用户明确要求时运行测试或程序验收。

## 9. 建模 Agent 的接入研究（2026-10-25）

本节补充自动建模如何使用 Agent。自动建图、以下工具及本文件拟议的生成接口仍未实现；本次先增加独立的[生活圈查询对话](life-circle-agent.md)，不让查询助手修改路网。未下载实际 OSM 区域、运行生成、测试或程序验收。

建模的数据流保持为：**原始数据源 → 规则建图 → 问题诊断 → Agent 调用受约束操作 → 冻结候选／版本／补丁 → 独立验证与编辑预览**。首版默认自动下载 OSM，用户无需预先准备 XML／PBF 文件；已有关于联网和独立 WGS-84 新区域的决定继续适用。

### 数据源与规则程序

先保存完整节点、道路引用、必要关系、通行和桥隧标签及来源摘要，再通过确定性程序生成基础 v2 图。程序负责坐标转换、路侧几何、空间查询、投影拆边和引用更新。显示轮廓在源拓扑之后单独生成，不能用 SVG 简化路径和坐标相近代替原始共享节点。

初始规则优先保留已记录的步道和过街，报告重复步道与权限冲突。普通道路分侧、双幅道路配对和复杂路口属于显式规则处理；没有可靠证据的入口、过街、闸门和层级关系保留待核。已有 OSM 记录、规则推定和实地核实是不同证据状态，模型不能通过自报置信度把前两种升级成已核实。

### Agent 只操作有明确边界的草稿

模型读取局部子图、源要素与诊断摘要，决定检查顺序并组织解释。可考虑的工具包括“读取局部源证据”“读取子图”“提出拆边／接入等受约束操作”“将操作应用到独立草稿”和“请求结构／路由检查”；这些是后续能力设计，不是当前已提供的接口。

每项操作应关联有效的源节点或边 ID、基础图版本、作用范围和证据。具体投影点、拆分位置、新 ID 与引用迁移由程序计算。模型不能自由输出整份替代图、任意坐标或仅以断头距离生成连接，也不能把让连通分量变少当作修复目标。证据不足时输出可定位的待核问题，不强行补线。

### 冻结、验证与回放

候选产物绑定源摘要、下载时间、生成器版本、配置和坐标原点；确认创建时使用冻结产物，继续复用 `engine-snapshot` 基线和 `manualGraphEdits`。旧基线或源版本变化时显式报告冲突；首版另存新区域，不自动迁移既有人工作业。

验证区分结构、路由语义、显示对齐和现实通行证据。现有 C++ 接受输入只说明图可被计算，仍需独立检查同侧转弯、不允许的换侧、过街等待、入口接入及桥隧交叉；几何面看起来完整不能代替路由证据。未来只有用户明确要求时才执行相应测试或程序验收，执行后再记录实际结果。

这种分工的好处是复用现有图算法、校验和编辑回放，让 Agent 聚焦需要根据反馈选择下一步的工作；取舍是保留疑点和人工核查，首版不承诺对任意地区完全自动确认真实通行。评估应分别记录错误连接、漏连接、路线偏差、待核量和人工修正时间；当前没有新的准确率或效率测量。
