# 主动局部精化与输入模型

日期：2026-10-28，工具栏说明更新于2026-10-30。状态：首版代码与编辑器接入完成，尚未完成运行验收。本次提交不包含自动修改后的区域数据。

这一阶段承接普通路口自动生成，把“不确定在哪里”与“核查它能改变什么”表达成可审阅的输入。借鉴主动采样对下一批位置的选择方式，以有限预算选择局部疑点，比较两个明确情景；审阅后更新草稿，再重新评估下一批。

## 使用流程

1. 本地后端和前端加载新代码后，打开路网编辑器，选中一个真实路网节点，在“进阶工具 → 检查与优化 → 局部精化”面板设为起点。
2. 设置本轮评估数量，默认10、上限30。等待的较短/较长情景默认为0/60秒，是用户可调整的假设范围，不是观测结果。
3. 点击评估，查看按情景影响排序的已评估项。其它候选分别标记为预算未评估、缺少可计算方案、已有审阅记录。
4. 点击候选定位，核对端口、过街位置及资料来源。确认是否允许过街或修改等待时间，并填写依据。
5. 应用到草稿，作为一次可撤销操作；点击“保存本地”才持久化。每次应用会清掉旧计划，需要重新评估。

```mermaid
flowchart LR
    A[当前画布与来源] --> B[带备选方案的精化输入]
    B --> C[起点与15分钟阈值初筛]
    C --> D[预算内单项情景对照]
    D --> E[按节点判定变化排序]
    E --> F[用户核查并应用草稿]
    F --> A
```

生成预览与精化计划互斥。编辑、拖动、撤销、重载或版本变化会清除旧计划；下载计划保留当次起点、参数、画布摘要和来源，便于解释结果。

## 输入模型

[build_refinement_inputs](../backend/app/refinement_inputs.py) 将每个疑点表达为：稳定ID、类型、米制位置、关联端点/边、来源和核查状态、备选方案、所需资料、已有审阅记录及是否可直接应用。

| 类型 | 当前输入依据 | 可比较的情景 | 审阅后的应用 |
| --- | --- | --- | --- |
| missing_crossing | 已生成普通路口同一源道路臂的两个实际路侧端口 | 不开通 / 假设允许过街并计等待 | 新建或撤回该精化项创建的过街；不删除别人的连接 |
| crossing_wait | 当前图里的过街边和等待参数 | 只把这一条边的等待改成较短 / 较长值 | 更新等待并记录依据 |
| junction | 来源不足或不适用普通模板的路口 | 缺少明确替代连接，暂不可评估 | 补充道路引用、层级或专用连接模型 |
| entrance | 区域POI有坐标但没有明确入口接入记录 | 缺少真实入口和接入路径，暂不可评估 | 先补入口资料，不自动最近邻接线 |

生成路口的端口通过node.generation和源边provenance关联，避免重新按距离猜测两侧。已存在其它人工过街的同一端口对不会再创建重复过街。普通共享步道交点和独立步行网络不会仅因未套普通路口模板而被列为错误。

POI使用区域包已有localPointMeters定位，沿用已记录的坐标校准，不把BD-09经纬度直接当引擎米制。设施坐标不是入口坐标，缺少接入路径时不计算虚构的设施覆盖变化。

## 影响评估

[plan_refinements](../backend/app/refinement_impact.py) 使用当前画布冻结快照。固定一个选定节点、900秒阈值、1.3米/秒步速，先求基线距离。边成本沿用长度/步速，过街再加等待；不调用外部路线API。

先用以下线索选出预算内候选，避免为全部疑点同时做情景计算：端口是否已在阈值内、是否有一端当前断连、端口到900秒边界的接近程度。这个初筛是启发式，不保证找出所有最重要的候选。

对每个预算内候选分别改变一个输入，其它输入固定：

- 未开通过街：宽松情景添加这一条虚拟过街，保守情景保持关闭。
- 已有过街等待：两情景分别采用用户设置的较短、较长等待。

在两个情景中分别取900秒内节点集合L、H，用 `|L △ H|` 记录可达判定改变的节点数，再按断连变化和可比较的有限耗时变化排序。它避免了只比较总节点数量而忽略具体节点变化。

跨断连时不存在有限的耗时差，maxTravelTimeDeltaSeconds为null，并另外报告reachableGapNodeCount。预算外、无法表达方案和已有审阅的项不填0分，也不给数字名次，避免把未知当成无影响。

每次只改一个候选，得到的是当前起点下的单项敏感性。两情景不是全图上下界，多项同时修改的收益不能相加；两个单独无影响的连接也可能组合后打开新路径。节点变化数受节点密度影响，不是面积、人口或设施覆盖数。此版本没有换掉正式分析中的C++多源Dijkstra，也没有完成正式分析结果页的自动反馈。

## 应用、保存和回放

[apply_refinement_decision](../backend/app/refinement_inputs.py) 仅在副本上应用一个明确选择。新过街/等待记录保存refinementReview；关闭过街的选择写到关联端口的refinementReviews，避免下次把明确拒绝的候选再次当作未知。

审阅包含inputId、选择、采用等待、依据、时间和user_reviewed_unverified状态。填写依据不会把记录自动升级成实地已核实。已有记录可重新修改；关闭操作只撤回该精化项自己创建的边。

每次建立候选时还会检查记录与当前边的存在性、端点、线形和等待是否一致。手工删除或修改后，旧记录作为previousReview展示，重新进入待评估；再次选择开放时保留当前自生成边的折线。端点/类型已经被改成另一种连接时，先转手工核对，避免用旧方案覆盖。

后端接口：

- POST `/api/v1/network-editor/refinement/plan`：当前revision/nodes/edges加originNodeId、budget、lowWaitSeconds、highWaitSeconds。返回输入、情景比较、预算状态与canvasRevision。
- POST `/api/v1/network-editor/refinement/apply`：当前revision/nodes/edges加inputId、decision、waitSeconds、evidenceNote。返回草稿，不写区域文件。

两接口复用本机访问限制、版本校验和现有图校验。前端采用同一change/history；现有PUT保存器把节点/边差异写成manualGraphEdits，因此打开、导出重建和恢复草稿均沿用现有持久化方式。没有增加C++路由字段；边的审阅元数据由现有编码器过滤，节点附加记录不参与引擎成本计算。
